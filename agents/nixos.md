# Working on this repository

This is Aniket's personal NixOS flake: the Dendritic pattern with `den` + `flake-parts` +
`import-tree`, so everything under `modules/` is auto-imported and a feature is one self-contained
file. Namespace: `blazar`.

- Aspects: `modules/aspects/<name>/*.nix`, declared as `blazar.<name>.nixos` /
  `blazar.<name>.homeManager`, referencing siblings via `includes = with blazar; [ ... ]`.
- Hosts: `modules/hosts/<host>/` — `andromeda` (ZFS + impermanence), `horologium` (LUKS +
  GRUB), `miranda`. Users: `modules/users/<name>/user.nix`. Adding a feature means adding it to a
  user's `includes` list, not to a host file.
- `flake.nix` is GENERATED by `flake-file`: never edit it. Edit `modules/flake/*.nix` and run
  `nix run .#generate-files`, which also regenerates `README.md` (from `modules/flake/readme.nix`),
  `.gitignore` and `.envrc` — so those are edited in their Nix modules, never directly.
- Custom packages live in `packages/<name>/package.nix` (auto-exported by
  `pkgs-by-name-for-flake-parts`); CI pushes them to the `heraldofsolace` Cachix cache.

## Commands

`just` lists recipes: `just build`, `test`, `switch`, `fmt`, `check`, `generate`, `update`,
`su`, plus `gate` / `gate-full` (the land gate, below). `nix develop` provides nixd, nixfmt,
statix, deadnix, nh, treefmt, the pinned `iii` binaries and more.

Prefer `nix build` / `nix flake check` over `just switch`: activating a live host, `sudo`,
`just boot`, disko and `nixos-anywhere` are the user's call, never a ticket's.

## Working a ticket

You are normally dispatched onto one kanban ticket and work in your own git worktree — the
absolute path is named in your task and sits under `worktrees/`. Never edit the primary
checkout at `/home/aniket/my-nix` while you hold a ticket: other agents are working there.
Use absolute paths inside your worktree path.

1. Claim the ticket, and arm your comment wake plus its done-watch, exactly as the
   `kanban/tickets/ticket-worker` skill describes.
2. Do the work in the worktree, then `git add -A && git commit` it. Untracked files are
   invisible to `nix flake check` and the gate refuses a dirty tree, so committing is what
   makes your work checkable at all.
3. Run `just gate` yourself before reporting: formatting must already be a no-op and the tree
   must be committed. `just gate-full` adds the flake's checks, evaluated but not built.
4. Report on the ticket with the exact commands you ran and their real output, then move it to
   `in_review`. The lead lands it after review; you do not merge your own branch.

## Conventions

- Format with treefmt (nixfmt, deadnix, statix, mdformat, taplo, shellcheck): `just fmt`.
  `agents/**` and `skills/**` are excluded on purpose — mdformat destroys their YAML
  frontmatter, and a profile with mangled frontmatter silently disappears from the roster.
- Secrets are SOPS-encrypted under `secrets/`. Never decrypt, print, or commit plaintext;
  `**/.env`, `**/*.pem`, `**/*.key`, `**/secrets/**` are non-accessible by policy.
- The same repo hosts the local iii engine (`worker-compose.yaml`, `config/`, `agents/`,
  `skills/`). That side is not part of the NixOS configuration: use the `iii-ops` profile.
- Report what you actually verified, and say plainly what you did not.
